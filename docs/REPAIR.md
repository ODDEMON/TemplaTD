# TemplaTD 修复方案 · 为什么玩不了，以及按什么顺序修

> **状态：已执行完毕（第四轮重做）。** 五个故障全部消除，方案里的探针已升级为常驻门禁。
> 这一份保留为**诊断档案**——它记录的是「为什么会有那次重做」，不是现状说明。
> 现状看 `docs/DESIGN.md` §9（架构）与 §11.2（第四轮记录）。
>
> 这一份是诊断报告 + 施工图，不是设计稿。
> 起因：上一轮 46 项内核冒烟 + 51 项界面冒烟全绿，但游戏实际打不通。
> **原因是那些测试调的是内部 API，不是真实点击。** 这一轮改用真实 DOM 事件复现。

---

## 0. 一句话结论

**这一版的「玩不了」不是玩法问题，是两个工程故障叠在一个设计缺陷上：
页面互相覆盖重写（玩家看到错的画面）、六项读数只有进度条没有数字（玩家读不出决策）、
120 张卡无从下手（玩家不知道该看哪件）。玩法骨架本身是通的——真实点击能落位、
能开战、能打到休整期。**

---

## 1. 复现方法（可重跑）

三个探针，全部只派发 DOM 事件，不调内部 API。
**这三个文件在第四轮已删除，其断言被吸收进常驻门禁 `test/smoke_play.mjs`**（下表是它们当初的职责）：

| 文件 | 干什么 |
|---|---|
| `test/probe_ui.mjs` | 打印六个页面「玩家实际看到的文本 + 能点的按钮」 |
| `test/probe_play.mjs` | 真实点击走完整循环：开新局 → 点元件卡 → 点格子 → 开战 → 结算 |
| `test/probe_place.mjs` | 逐个元件打印「为什么放不下」的拒绝理由与占据表 |

**好消息**（这条循环是通的，证据）：

```
#0 frame 12格 成本36 墙 → 落位 [0,0]  ok
#1 tri    6格 成本14 塔 → 落位 [4,0]  ok
#2 dia    5格 成本21 塔 → 落位 [6,0]  ok
#5 cross  9格 成本34 塔 → 落位 [9,0]  ok
开战 → 阶段=battle → 战场页显示「第 1 波 / 共 10 波 基地 15/15 塔 2 墙 1」
```

## 2. 五个故障

### A · 致命 · 六个页面共用同一个宿主元素

**现象**：在战场页跑 121 次时钟之后，面板文字变成了——

```
建造台 FORGE 花部署预算把元件建成炮塔与墙……
这一局已经开战，部署改不了了。   [开一局新的]
```

**机理**：`app.go(id)` 把 `#panel` 这个**同一个 div** 传给 `mount(h)`，每个 mod 存下
`host = h`；而 app 的时钟对**全部**已注册 mod 调 `tick(100)`。任何 mod 的 `dirty`
被总线事件（`run` / `restore`）置起来，它就把自己重画进那个共享宿主。

所以：**在战场上会看到建造台，在建造台上会看到战场**。切换页面后画面被别的页面随机覆盖。
这一条单独就足以解释「完全玩不了」。

**修法**（改动小，风险低）：
1. `go()` 每次 `panel.innerHTML=''` 后**新建一个子 div** 交给 `mount`——旧 mod 写进已被摘除的节点，无害。
2. 时钟**只 tick 当前页**（`cur.tick`），不再遍历全部。
3. 各 mod 补 `unmount()`：清 `host = null`，解绑总线监听。

### B · 致命 · 六项读数只有进度条，没有数字

`world/mods/lib.js` 的 `bar(v)` 只输出 `<i style="width:N%">`，没有任何数字。

这一部的命脉是「读数决定塔属性」（图鉴里写得清清楚楚：对称→弹数、重复→攻速、
通透→射程、匀质→伤害、环络→连锁与减速、轮廓→近战与生命）。
**玩家看不到读数，就读不出决策**——核心映射不可感知，游戏退化成「随便点几件开打」。

**修法**：`bar()` 出条 + 两位小数数字；建造台元件卡、元件库、图鉴三处同步。

### C · 认知负担 · 120 张卡没有抓手

建造台一次渲染 120 张元件卡，元件库 120 行无分页、无筛选、无排序。
玩家面对 120 件，`对称 0.42` 和 `对称 0.49` 哪个值得带——没有任何抓手。

**修法**：建造台列表分页（24/页）+ 按「塔种 / 成本 / 单项读数」排序 + 关键词筛选。

### D · 静默失败 · 放不下不说为什么

18 格的「拱」在默认朝向下**全场找不到一个合法位**（`probe_place` 实测），
点击后只往总线写一条日志，卡片不置灰、不提示。玩家以为游戏坏了。

**修法**：选中元件后实时把**全部合法落点**标成绿点；一件合法位都没有时，
卡片置灰并写明「这件放不下，按 R 换个朝向」。

### E · 接口 · `deployOk` 不守空

`r.battle` 是懒创建的（`newRun` 之后是 `null`，第一次 `add` 才生成），
而 `deployOk(b, ...)` 直接读 `b.occ`，传 null 就抛。
现在靠调用方自觉写 `r.battle || TD.start(...)`——三个调用点里只有一个写了。

**修法**：`deployOk` 内部补 `if (!b) return ...`；或者让 `newRun` 直接把棋盘建出来。
后者更干净，但要确认 `begin()` 不会重复初始化。

## 3. 修复顺序

| 序 | 故障 | 为什么排这个位置 | 改动量 |
|---|---|---|---|
| 1 | **A 宿主与时钟** | 不修它，修别的也看不见效果 | 小（app.js + 六个 mod 加 unmount） |
| 2 | **B 读数出数字** | 核心映射的可见性，这一部的命 | 小（bar() + 三处调用） |
| 3 | **D 合法落点提示** | 把「静默失败」变成「看得见的规则」 | 中（ghost 全量计算） |
| 4 | **E 接口守空** | 顺着 3 一起做，零额外成本 | 极小 |
| 5 | **C 列表分页排序** | 认知负担，不致命但决定耐玩度 | 中 |

**1 和 2 是必修**，做完游戏就能打通并看得懂。3–5 是让它「愿意玩第二局」。

## 4. 做完后必须补的验证门禁

上一轮的教训：绿了的测试和能玩是两件事。修完之后把 `probe_play.mjs`
提升为常驻门禁 `test/smoke_play.mjs`，断言：

1. 点「开一局新的」之后，元件卡数 > 0 且格子数 = 160
2. 点卡片 → 点格子 → **已部署数 +1**（不是静默失败）
3. 点「开战」→ 阶段变 `battle`
4. 在战场页走 N 次时钟后，**面板文本仍含「战场」**（A 的回归断言）
5. 面板里六项读数出现**数字**（B 的回归断言）
6. 一路点到结算，阶段变 `over` 且卷宗出现 1 条记录

## 5. 没做的事（诚实记账）

- 以上全是**工程故障**，不含玩法改动。玩法层的问题（一局之内缺目标、
  120 件选哪件没有引导、休整期升级的取舍是否成立）要等能玩通之后再评估。
- `probe_place` 显示大件容易放不下，这可能不只是提示问题——
  **16×10 的战场对 18 格元件是否太小**，是个待验证的平衡问题，
  建议修完 1–4 之后拿真实游玩数据判断，现在不动数值。
